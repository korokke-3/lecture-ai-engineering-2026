- 直した基準と、書き足した方針：根拠の基準の下に「用語集にない語を、『用語集にはない』と伝えたうえで一般的に説明するのは、推測による断定にはあたらない（pass）」と書き足し、「まだ決めていないこと」からこの論点を消した。用語集にないことを先に伝えていれば、利用者は一般的な説明を用語集の裏付けがない情報として受け取れるので、断定にはあたらないと考えた。

- 講師のラベルと自分のラベルで判定が違った項目と、そう判定した理由：`app.judge --compare` で比べたところ、5 つの基準すべてで 10/10 一致し、判定が違った項目はなかった。「迷った」を付けた項目も、講師と同じ #05 だった。#05 は基準の「まだ決めていないこと」にそのまま当てはまるので、基準だけでは決められないと判断した。

## 宿題

- 取り組んだレベル：発展

- やったこと：
  - ベンチマークとして SWE-bench Verified を選んだ。
    - データセット：https://huggingface.co/datasets/princeton-nlp/SWE-bench_Verified
    - 作成手順の出典：OpenAI「Introducing SWE-bench Verified」https://openai.com/index/introducing-swe-bench-verified/ と、元の SWE-bench の論文 arXiv 2310.06770
  - Hugging Face の Dataset Viewer で 500 件すべてのメタデータを取得し、リポジトリと難易度の分布を数えた。
  - 難易度の異なる 4 件の問題について、issue の本文、正解パッチの大きさ、テストの数を読んだ。

- 結果：

  **データセットの中身**

  1 件の問題は、GitHub の Python リポジトリで実際に解決された issue 1 つに対応する。エージェントは issue の本文とリポジトリを受け取り、コードを編集して issue を直す。採点はテストの実行で行う。元の PR に含まれていたテストのうち、PR の前は失敗し後は成功するものを FAIL_TO_PASS と呼び、これがすべて通れば issue が直ったとみなす。前後どちらでも通るべき PASS_TO_PASS テストも通れば、既存の機能を壊していないとみなす。テストはエージェントに見せない。

  500 件を数えた結果は次のとおりである。

  - リポジトリは 12 個で、django が 231 件と半数近くを占める。続いて sympy が 75 件、sphinx が 44 件、matplotlib が 34 件、scikit-learn が 32 件である。
  - 注釈者が見積もった修正時間は、15 分未満が 194 件、15 分から 1 時間が 261 件、1 時間から 4 時間が 42 件、4 時間超が 3 件である。
  - 1 件あたりの FAIL_TO_PASS テストの数の中央値は 1、PASS_TO_PASS テストの数の中央値は 50.5 である。

  **読んだ問題の要約**

  | 問題 | 見積もり | 内容 | 自分なら解けるか、LLM にとって何が難しいか |
  |---|---|---|---|
  | psf__requests-1142 | 15 分未満 | GET リクエストにも Content-Length ヘッダが常に付き、一部のサーバがそれを拒否するという報告。正解パッチは 1 ファイルで、追加 2 行と削除 1 行 | 解ける。ヘッダを付ける場所を探し、付けない条件を決めるだけである。LLM でも難しくないが、どの条件で付けないかを issue から読み取る必要がある |

  4 件を読んで、見積もり時間の差はパッチの行数よりも、原因を突き止めるのに必要なコードベースの理解の深さで決まっていると感じた。django の問題は数行の修正で 1〜4 時間と見積もられている。

  **作成に関わった人数と手順**

  元の SWE-bench は、Princeton の Jimenez らが 2023 年に公開した。12 の人気 Python リポジトリから約 9 万件の PR を集め、issue を解決していてテストを変更した merged PR に絞り、さらに実際に実行して FAIL_TO_PASS テストが 1 つ以上あるものに絞って、2,294 件を作った。この段階は自動の手順で、人が 1 件ずつ確認してはいない。

  SWE-bench Verified は、OpenAI が SWE-bench の著者と共同で 2024 年 8 月に公開したもので、元のテストセットから人が選別した 500 件である。手順は次のとおりである。

  1. OpenAI のエンジニアが 50 件に高い確度でラベルを付け、注釈者の候補を選ぶテストに使った。このテストに合格した人だけが作業に参加した。
  2. Python の経験が豊富なプロのソフトウェア開発者 93 人が、元のテストセットから無作為に選んだ 1,699 件を確認した。1 件を別々の 3 人が独立に見た。
  3. 観点は 2 つで、issue の記述が十分に特定されているかと、FAIL_TO_PASS テストが妥当な解まで落としてしまわないかである。それぞれに 0 から 3 の 4 段階の深刻度を付けた。あわせて修正にかかる時間を見積もり、その他の重大な問題を自由記述で報告させた。
  4. 3 人のうち最も深刻なラベルを採用し、どちらかの観点で深刻度 2 以上の件と、その他の問題が報告された件を除いた。1 人でも問題ありとすれば落ちる、保守的な集約である。
  5. その結果、38.3% が記述不足、61.1% がテストが不適切と判定され、全体の 68.3% が除かれた。残った件から、1 時間を超える難しい問題をできるだけ含めたうえで無作為に選び、500 件にした。
  6. 採点には、Docker のコンテナで環境を固定した新しい評価ハーネスを使う。環境の違いで正しい解が不合格になる問題を減らすためである。

- 気づき・疑問：
  - テストで自動採点できるベンチマークでも、テストそのものが妥当かは人が見ないと分からず、元のデータの約 3 分の 2 が除かれた。自動採点の前提を人が検証するという構図は、今日 LLM の採点を人のラベルと比べたのと同じだと感じた。
  - 1 人でも問題ありとすれば捨てる方針は、良い問題も多く捨てる代わりに、残った問題の信頼性を上げる。10 件しかない今日の評価セットでは同じことはできないので、割れた論点を基準に書き足して判定をそろえる方が現実的である。
  - django が半数近くを占めるので、点数は django のコードベースに強いかどうかに引っ張られる。リポジトリごとの正答率も見ないと、点数の意味を読み違えると思う。
  - 疑問：問題は公開リポジトリの issue と PR から作られているので、正解パッチが事前学習のデータに含まれている可能性がある。OpenAI の記事も汚染の可能性を限界として挙げている。点数のうちどれだけが記憶によるものかを、このデータセットだけで区別する方法はあるのか。
