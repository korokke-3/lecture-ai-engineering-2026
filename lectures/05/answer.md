### 解きたい質問

講義資料への質問のうち、回をまたぐものを解けるようにしたい。たとえば第2回 p.50 は「第1回の『モデル・手法の大別』の具体版」と書いており、FTとRAGの使い分けを聞かれたら第1回 p.48 と第2回 p.46・47・50 を合わせて答えるのが望ましい。演習で既存のGraphを動かすと、入口のページと同じ回の前後ページばかりが返り、別の回の根拠ページには届きにくかった。

### 既存のGraphの問題点

`app/retrieval.py`の`search_graph`を読み、次の3点を問題と考えた。

1. 入口が質問全体の埋め込み1つだけである。回をまたぐ質問では、入口が片方の回に偏る。
2. 用語ノードを経由する2 hop目で、LLMやRAGのように多くのページに出る用語もたどる。そのため質問と関係の薄いページが候補に増える。
3. 候補の順位がhop数と用語の接続数だけで決まり、質問との近さを見ていない。上位10ページを返すので、入力トークンも多い。

`graph.json`には用語どうしの`related_term`という関係が141本あるが、既存のGraphは使っていなかった。また、本文中の「第N回の『…』」という回をまたぐ参照は、関係として持っていなかった。

### 設計（`app/graph_plus.py`）

データの形と持ち方は次のとおりである。

| 要素 | 内容 | 持ち方 |
|---|---|---|
| ページノード | 第1〜3回の本講義214ページ | `lectures.json`から読む |
| 用語ノード | 72語と別名 | `graph.json`から読む |
| `next_page` | 前後ページ | `graph.json`の関係をそのまま使う |
| `mentions` | ページに用語が出現する | 同上 |
| `related_term` | 用語どうしの関連 | 既存のGraphで未使用だったものを使う |
| `cites` | 回をまたぐ明示的な参照 | 本文の「第1回の『…』」「第1回 9ページ」「第1回で見たRSI」を正規表現で読み、参照先のページと両向きに結ぶ。3組できた |
| ページの埋め込み | 768次元 | 索引DB`index.sqlite3`から読む。追加の埋め込みAPI呼び出しはない |

検索の手順は次のとおりである。

1. 入口を3種類にする。1つ目はベクトル検索の上位3ページ、2つ目は質問に名前か別名が出てくる用語を含むページである。3つ目は、質問が「第N回」を指定しているときの、その回の中で類似度が最上位のページで、これはTreeで回を選んでから中を探すのと同じ発想である。
2. 入口から1段だけ広げる。たどる関係は`next_page`、`cites`、`related_term`の3つにする。用語経由で広げるのは、質問の用語に`related_term`でつながる用語だけに限る。
3. 候補を、質問の埋め込みとページの埋め込みの内積で採点する。質問の用語を含むページ、指定された回のページ、`cites`でつながったページには少し加点する。
4. 返すページを最大6件選ぶ。最上位のページを取ったあと、質問の用語と指定された回が少なくとも1ページずつ含まれるように補う。回の補完では、選んだページが本文で参照している先を優先する。内容がほぼ同じページ、つまり埋め込みの内積が0.97以上のものは片方だけ返す。各ページには選ばれた経路`reasons`を付け、`--trace`で表示する。

この形を選んだ理由は3つある。第1に、質問の用語と回の指定は、回をまたぐ質問で最も確かな手がかりであり、埋め込み1つに混ぜると薄まる。第2に、本文が自分で別の回を名指ししている箇所は、作り手が意図した関係なので信頼できる。第3に、候補をグラフで広げても、最後に質問との近さで絞らないと入力が増えるだけである。Treeのようにモデルが目次を何度もたどる方式は呼び出し回数が増えるので、回を選ぶ発想だけを検索の入口に取り入れた。

ほかの変更として、`app/tools.py`に`search_graph_plus`ツールを、`app/agent.py`に`--graph-plus`モードと専用の指示文、trace表示を、`app/config.py`に`GRAPH_PLUS_MAX_RESULTS = 6`を追加した。`tests/test_graph_plus.py`はAPIを呼ばないテストで、既存のテストを含む23件が通る。比較には`scripts/compare_graph_plus.py`を使った。

### 改善した例

- q6では、改良版は1回の検索で第1回 p.10と第3回 p.54・58を取り、入力2,900 tokensで答えた。既存Graphは検索を4回繰り返し、入力が42,964 tokensになった。traceでは、第1回 p.10が「lecture: 第1回の中で類似度が最上位」という経路で入っていた。確認用の質問でも、回の指定を入口にする規則が効いた。
- q4では、既存Graphは前後ページを広げるうちに第3回 p.13を落とし、p.65を引用した。改良版は根拠の3ページをすべて含み、入力tokensは既存Graphより約4割少なかった。
- 7問を通して、改良版はモデル応答が2回で済むことが多く、入力tokensと推定費用は3方式で最も少なかった。返すページを6件に絞っても、根拠が足りずに検索をやり直すことは増えなかった。

### 残る失敗

- q2の回答では、改良版も第1回 p.48を引用しなかった。検索だけの比較では4/4だったが、エージェントは質問を「講義チャットボット Fine-Tuning RAG 第1回 第2回」という検索語に書き換えていた。この検索語では、第1回を補う時点で第2回 p.50がまだ選ばれておらず、`cites`が効かずに第1回の類似度最上位であるp.49が入った。回の補完を、点数順の選択の後に回す必要がある。
- q3とq7では、質問の「エージェント」が用語「AIエージェント」に一致した。この用語は多くのページに出るので、第3回 p.54のRSIやp.71の一次情報のような関係の薄いページが入口になった。既存Graphで問題にした一般的な用語の問題を、入口側で再び起こしていた。用語の加点を、その用語が出るページ数で割り引く必要がある。
- q7では、3方式とも第2回 p.22を取れなかった。質問が第2回と第3回の両方を含むため、第2回の中での類似度最上位が「次回：AIエージェント」のp.62になり、p.22は第2回の中で3位だった。回ごとに質問を分けて埋め込まないと、この種の質問は解けない。
- 実装中にも不具合が2つあった。1つ目は、空白を消してから英数字の境界を調べたため、エージェントの検索語「Fine-Tuning RAG」から用語を取れなかったことである。2つ目は、trace表示の変数名が結果の変数を上書きしたことである。どちらも直してから、比較を最初から取り直した。
- 時間は生成APIの待ち時間に大きく左右される。改良版のツール単体の処理は約0.07秒だった。修正前の実行では、q6の改良版が291秒かかったが、これはAPIの再試行によるものだった。各条件1回ずつの測定なので、時間の差は誤差の範囲と考える。

### 考察

検索だけを見ると改良版の効果ははっきりしていた。一方、エージェントを通すと、モデルが検索語を書き換えるため、効果は小さくなった。質問文を前提に検索器を設計しても、実際にツールへ届くのはモデルが作ったキーワード列である。検索器の評価は、モデルが実際に送る検索語でも確かめる必要があると分かった。

採用するかについては、講義資料のQ&Aのように「第N回」の指定や回をまたぐ参照が多い用途なら、改良版を採用したい。根拠に届く割合が上がり、入力tokensが既存Graphの約4分の1、ベクトル検索の約3分の2になったからである。ただし、上に挙げた3つの課題は先に直したい。回の補完を後に回すこと、一般的な用語を割り引くこと、回ごとに質問を分けることである。また、q1〜q5は規則を決めるときに見た質問であり、確認用の質問は2問しかない。採用を決める前に、確認用の質問を増やし、各条件を複数回実行して比べたい。

疑問として、`cites`の関係は3組しか取れなかった。講義資料の作り手が回をまたぐ参照を本文に書く量は限られる。目次の見出しどうしの類似度から関係を自動で作る方法と比べて、どちらが信頼できるかを試したい。
